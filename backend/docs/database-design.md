# Database Design

PostgreSQL 16+ (tested on 18). Schema owned by **Flyway** (`src/main/resources/db/migration`); Hibernate runs with `ddl-auto=validate`. Demo data lives in `src/main/resources/db/demo` and is only applied with the `demo` profile.

## Conventions

- `uuid` primary keys generated by the application.
- `timestamptz` for instants, `date` for calendar dates.
- Enums stored as `varchar` + `CHECK` constraints (readable, easy to evolve with a migration).
- Structured JSON payloads stored as `text` (serialized by the application; never queried by content).
- `version bigint` for optimistic locking on mutable aggregates.

### `task_dependencies`
id PK · project_id · predecessor_task_id · successor_task_id · type CHECK = 'FINISH_TO_START' · created_by FK→users SET NULL · created_at.
UNIQUE (predecessor_task_id, successor_task_id); CHECK predecessor ≠ successor; FK (predecessor_task_id, project_id) → tasks(id, project_id) CASCADE; FK (successor_task_id, project_id) → tasks(id, project_id) CASCADE. Indexes (project_id), (successor_task_id).

## Referential integrity highlights

- Project data cannot leak across workspaces: memberships reference `(workspace_id, user_id)` pairs; dependencies reference `(task_id, project_id)` pairs.
- Deleting a user is not exposed by the API; FKs are defined defensively (RESTRICT on authored data, SET NULL on assignments).

## Migration strategy

- Versioned migrations `V{n}__description.sql`, never edited after release; one migration per logical change.
- `V1__identity.sql`, `V2__workspaces_projects.sql`, `V3__tasks.sql`, `V4__risk.sql`, `V5__inbox.sql`, `V6__ai_generations.sql`.
- Demo seed `db/demo/R__demo_seed.sql` is a *repeatable* migration, added to Flyway locations only with the `demo` profile. It is idempotent (`ON CONFLICT DO NOTHING` / `NOT EXISTS`) and never occupies a version number, so it cannot block future versioned migrations.
- Flyway runs automatically on application startup (no separate Maven Flyway plugin); `FlywayMigrationIT` validates every migration against a fresh PostgreSQL container.

## `ai_generations`: AI generation log (`V6__ai_generations.sql`)

Telemetry, not a system of record: best-effort asynchronous inserts in their own transaction (a failed write only loses the entry). Prompts, model output text and credentials are never stored. Rows are deleted after 90 days by a daily job (`AiGenerationLog.purgeExpired`).

## Important access patterns

| Pattern | Query / index |
|---|---|
| Authorize project access | `workspace_memberships (workspace_id,user_id)` + `project_memberships (project_id,user_id)` unique lookups |
| List tasks with filters | `tasks (project_id, status)` partial index, Spring Data `Specification`, paged |
| Load analysis snapshot | all non-archived tasks + dependencies + members of one project (bounded by project size) |
| Periodic job | `projects WHERE status='ACTIVE'` paged by id |
| Reconcile | `risk_assessments WHERE project_id=?` (all identities, active + resolved) |
| Delivery sweeper | `risk_assessments (delivery_status, next_delivery_attempt_at)` |
| Inbox listing | `inbox_items (recipient_id, last_delivered_at DESC)` + filters, paged |
| Generation history of a risk | `ai_generations (assessment_id, created_at DESC)`, paged |
