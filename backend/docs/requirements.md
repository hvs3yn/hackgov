# Requirements

Foresight is a backend for a collaborative project/task manager whose differentiator is **proactive risk management**: it detects emerging delays from real project data, explains them with evidence, recommends concrete actions and delivers them to the right people through a persistent **AI Inbox**.

## 1. User roles and permissions

### Workspace roles

| Role | Capabilities |
|---|---|
| `OWNER` | Everything an ADMIN can do, plus grant/revoke `OWNER`. A workspace always has ≥ 1 owner. |
| `ADMIN` | Rename workspace, add/remove members, change roles up to `ADMIN`, **implicit LEAD access to every project in the workspace**. |
| `MEMBER` | See the workspace, create projects (becomes LEAD of them), access only projects they are a member of. |

### Project roles (explicit project membership; requires workspace membership)

| Role | Capabilities |
|---|---|
| `LEAD` | Edit/archive the project, manage project members, edit/assign/archive any task, manage dependencies, trigger risk analysis. |
| `CONTRIBUTOR` | View everything in the project, create tasks, edit/progress/status-change tasks they are **assigned to or reported**, self-assign unassigned tasks, add/remove dependencies on tasks they may edit, trigger risk analysis. |
| `VIEWER` | Read-only access to the project, its tasks and risks. |

Effective project role = `LEAD` if workspace `OWNER`/`ADMIN`, otherwise the project membership role, otherwise **no access**. Resources a user cannot see return **404** (no existence leak); visible resources with insufficient permission return **403**.

## 2. Functional requirements

| ID | Requirement |
|---|---|
| FR-1 | Users register with full name, email (normalized to lower case, unique) and password; log in; renew tokens with a rotating refresh token; log out; read their profile. |
| FR-2 | Users create workspaces (creator = OWNER), list their workspaces, rename them, and manage members by email and role. |
| FR-3 | Workspace members create projects with name, description, optional start date and deadline; list/read/update/archive/restore projects; manage project members and roles. |
| FR-4 | Project members create tasks (title, description, priority, assignee, start/due dates, estimated/actual hours), list them with filtering (status, priority, assignee, due range, overdue, text), sort and pagination, read, update details, assign, change status following the lifecycle, update progress, archive. |
| FR-5 | Finish-to-start dependencies between tasks of the same project; self-dependencies and cycles are rejected; tasks cannot move to `IN_PROGRESS`, `IN_REVIEW` or `DONE` while a prerequisite is unfinished. |
| FR-6 | Every meaningful task change is recorded in an activity history readable through the API. |
| FR-7 | A deterministic risk engine evaluates six rules (overdue, approaching deadline, stalled, blocked dependency, project deadline, workload imbalance), producing a 0–100 score, severity, confidence, contributing factors, evidence and affected tasks. |
| FR-8 | Risk assessments are persisted with a lifecycle (detected → escalated/mitigated/updated → resolved → reopened) and an event history. |
| FR-9 | Each delivered risk gets an explanation and prioritized recommendations generated by the configured AI provider, validated against a schema, with a deterministic fallback when no provider is configured or the provider fails. |
| FR-10 | Risks at or above the notification threshold are delivered to relevant, authorized users' AI Inbox (assignee, project leads, and – for high severity dependency risks – affected/blocking assignees). One inbox item per (risk, recipient); re-surfaced only on material change. |
| FR-11 | Users list/filter/sort/paginate their inbox, read an item, mark it read/unread, acknowledge or dismiss it, get an unread count, and navigate to the related project/task/risk. |
| FR-12 | Risk analysis runs on a schedule for active projects and shortly after relevant changes; leads/contributors can trigger it on demand. |
| FR-13 | Project risk summary: overall level, counts per severity/category, top risks, last analysis time. |

## 3. Non-functional requirements

| ID | Requirement |
|---|---|
| NFR-1 Security | BCrypt passwords, stateless JWT access tokens (15 min), rotating refresh tokens stored hashed, resource-level authorization on every endpoint, explicit CORS, no secrets in source. |
| NFR-2a Storage | PostgreSQL holds all business data; MongoDB holds only the AI generation log (telemetry, 90-day TTL). |
| NFR-2 Integrity | PostgreSQL is the authority for uniqueness and referential integrity (FKs, unique and check constraints, composite FKs keeping project data inside its workspace). Flyway owns the schema; Hibernate only validates it. |
| NFR-3 Concurrency | Optimistic locking for task/project edits (client sends `version`), per-project write serialization for dependency/graph changes and analysis reconciliation, DB-unique dedupe for assessments and inbox items. |
| NFR-4 Reliability | Analysis is idempotent; AI calls never run inside a DB transaction; failed deliveries are retried by a sweeper; no lost alerts on crash (DB-backed delivery state). |
| NFR-5 Explainability | Every score is the sum of documented factors; scores are not presented as probabilities. Facts shown to users come from system data, never from the LLM. |
| NFR-6 Operability | Actuator health/info, request correlation IDs, structured logging, Docker Compose for DB + app, OpenAPI docs at `/swagger-ui.html`. |
| NFR-7 Performance | All collection endpoints paginated (max page size 100). Risk analysis loads one project at a time with bounded queries. Target scale: hundreds of tasks per project. |
| NFR-8 Testability | Risk engine is pure Java (no Spring/JPA), driven by a `Clock`; AI provider mocked in tests; integration tests on real PostgreSQL via Testcontainers. |
| NFR-9 Portability | Runs locally without any AI key; one `docker compose up` brings up PostgreSQL, MongoDB and the backend. |

## 4. Main user journeys

1. **Onboard**: register → create workspace → invite teammates by email → create project → add project members.
2. **Plan**: create tasks with owners, due dates, estimates → link dependencies (e.g. *API integration* depends on *Authentication*).
3. **Execute**: assignees move tasks through the lifecycle and report progress; history is recorded.
4. **Get warned**: Ulvi's *Authentication* task is due tomorrow at 20 % with no recorded progress for 2 days; *API integration* depends on it. The engine raises an `APPROACHING_DEADLINE` risk (HIGH) listing the dependent tasks; Ulvi and the project lead receive an inbox item with explanation and actions (split work, request review, re-sequence independent tasks, reassess the integration date).
5. **React**: the lead opens the item, follows `taskId` to the task, reassigns/splits; the user acknowledges the item.
6. **Resolve**: once the task is done the next analysis marks the risk `RESOLVED`; the inbox item shows `riskStatus = RESOLVED`. If the task slips again, the same risk is `REOPENED` and the item resurfaces as unread.

## 5. MVP boundaries

In scope: everything in §2, REST only, single deployable (modular monolith), PostgreSQL, scheduled + change-triggered analysis, one external AI provider (Anthropic) plus deterministic fallback, demo seed data behind a `demo` profile.

## 6. Out of scope (explicit)

- Frontend (separate TypeScript project), WebSocket/push/e-mail delivery.
- Invitations to not-yet-registered users, password reset, e-mail verification, OAuth/SSO, MFA.
- Rate limiting of login attempts (documented as a known limitation).
- Calendars, working hours per person, holidays, cross-project workload (workload rule is project-scoped).
- Dependency types other than finish-to-start, sub-tasks, milestones as a separate entity (the project deadline acts as the milestone), comments, attachments.
- Statistically calibrated probabilities of delay.
- Multi-instance job coordination beyond DB-level idempotency (no distributed lock service).
